# What a forge actually does — signals, and where each one lies

Read wherever a skill acts on what a forge reports. Every row is a behaviour that
cannot be derived from a document or guessed from a field name: it was measured, and
the measurement is what the row carries.

[`invariants.md`](invariants.md) says how to read any signal. This file says what
these particular signals do. A new measurement is a **row**, never a paragraph
somewhere else — that is what keeps this knowledge from being rewritten five ways in
five files.

GitHub unless a row says otherwise. Where GitLab has a counterpart, the row names it;
where a row is unmeasured on GitLab, it says so rather than implying symmetry.

## Checks and their aggregate

| signal | what it actually is | measure instead | where it does not apply |
|---|---|---|---|
| "every check on the head has finished" | true before the run is over. Checks register in waves — one measured head had them start at `19:34:16`, `19:34:27`, `19:35:37` and `19:42:06` — so a moment with none running is ordinary, not final | the named aggregate the base requires, plus `mergeStateStatus` | a base that runs no aggregate: there the count is what there is, and the report says the guarantee is weaker |
| the aggregate check itself | **born last, after the others finish.** Measured: the aggregate started at `19:42:06`, three seconds after the last of the other nineteen completed at `19:42:03`. At the instant "all finished" became true, it did not exist | wait for it by name, not for the count to settle | — |
| the `commits/<sha>/status` feed | **a second feed, not a view of the first.** It carries the older commit statuses, which an external CI may post to and nothing else does — so a reader of `check-runs` alone is blind to it however red it is | read both, and keep them apart | — |
| that feed's `state` | **`pending` over an empty list is its EMPTY answer, not a run in flight.** Measured on seven commits across four repositories, every one of them with all `check-runs` completed: `"state": "pending", "statuses": []` | the rollup only beside a non-empty list; a poll on `.state` alone never exits | a commit that genuinely carries statuses |
| a check-run's `name` | **not unique on a commit.** Measured: one merge commit carried 22 runs over 13 distinct names — four names three times each and one twice, one leg of a matrix apiece. Keyed by name, 9 of the 22 collapse into a row already counted and go unread | key by `id`; report by name | — |
| the set of checks on a merge commit | **not the set the head carried.** Measured on one pull request: the head ran 9, the merge commit 22 — the extra fourteen from audit and dependency workflows scoped to a push, which no pull request triggers. The reviewer's own check goes the other way and is absent there | read the merge commit's own feeds after the merge lands, and the commit before it to learn what this base runs on a push at all | a base whose workflows all run on pull requests too |
| `statusCheckRollup` on the pull request | **not the set on the head.** Measured across two repositories: the head carried one check the rollup never showed, and the difference was always `copilot-pull-request-reviewer` | the head's own `check-runs` feed for completeness; the rollup for what gates the merge | a pull request no reviewer was requested on — there the two agree |

A check living outside the rollup has no moment at which "every check finished" holds
while the review is open. That is a property of the **pull request**, not of a commit:
where there is no request standing, the count does have a moment of truth.

## Merging

| signal | what it actually is | measure instead |
|---|---|---|
| `squash_merge_commit_message` | **`COMMIT_MESSAGES` is the default, and it was in force in all five repositories measured** — the landing commit's body becomes the branch's whole history glued together, the review rounds included, and no edit afterwards changes what landed | pass the body explicitly (`--body` / `--body-file`) rather than letting the default compose it |
| `squash_merge_commit_title` | disagrees between repositories about whether the pull request's title reaches the commit at all — `PR_TITLE` and `COMMIT_OR_PR_TITLE` both measured in the same set | read the setting, or pass `--subject` |
| `git branch -d` | **tests containment against the branch's upstream, not against the branch you merged into.** Measured after a squash merge: it deleted the branch, saying so out loud — `deleting branch 'feature' that has been merged to 'refs/remotes/origin/feature', but not yet merged to HEAD` | the forge's record: the request is merged and its `headRefOid` is contained in the target |
| a ref-level containment check after a squash | **never passes.** Squash writes a new commit, so `merge-base --is-ancestor` answers no and `branch --merged` omits the branch, however completely the work landed | the same forge record |
| `gh pr list --head <branch>` | **a branch NAME, matched across every head repository, forks included.** Measured on `nodejs/node`: `--head main` answered with six open requests whose heads live in six different owners' forks. A second request on *this* ref is told apart only by identity — `headRepository` on both the request and the listing | compare `headRepository.id`, or `nameWithOwner` where no id is given, and treat a listing that carries neither as unknown rather than as a difference |
| `merge_commit_sha` on `/commits/<sha>/pulls` | **returned, and not in the endpoint's documented response schema** — measured on a live request, where `merged_at` is documented and this is not. It is what a containment proof needs, so its absence has to read as *no proof* rather than as an error | take it where it is there, and fall back to the request being unproven where it is not |

## Review

| signal | what it actually is |
|---|---|
| the size of a change | **does not predict the automated reviewer's verdict.** Measured over 16 merged pull requests: 3717 lines across 4 files was approved, 709 lines across 11 files was approved, and 686 lines across 10 files was not. Two changes of nearly equal size and shape, different answers |
| the body of an automated review | **a layout the forge publishes none of, and it does not hold still.** Measured over 13 543 Copilot reviews across four repositories in eleven days: two layouts arrived interleaved rather than one replacing the other — the one a degraded run posts carries neither the labels nor the counts the other does — and the favourable verdict came under two headings, one on every review that approved and the other on every review that did not. GitLab's counterpart is unmeasured |
| the files an automated review did not review | **named in its body and nowhere else — where it names them at all.** Measured over 13 543 Copilot reviews: 413 carried a `Files not reviewed` block, every entry in it a generated `.yaml`; one such review landed `APPROVED` beside a `success` check-run, and the one review that could review no file at all landed `COMMENTED` with no check-run of its own. Where no block names them, the count below is the only report. GitLab's counterpart is unmeasured |
| the heading of an automated review body | **three, and the third is the one findings hide under.** Measured over 94 Copilot reviews on three pull requests of one repository: `🟢 Approved`, `🟡 Changes recommended` and `🔵 Needs a closer look`. 54 counted no new inline comment, and 53 of those carried the third heading. GitLab's counterpart is unmeasured |
| the sentence under that heading | **a finding of its own, not a summary of the others.** Measured over the same 94: on the 53 reviews counting no new comment under `Needs a closer look`, that sentence asserted a defect — and each one checked against the code was real. 45 of them carried a suppressed block too, and on one the block named a different finding in a different file, so a reading held to the block's count closed one short |
| `Files reviewed: N/M` in an automated review body | **a second report of what went unreviewed, independent of the block.** Measured over the same 94: no review carried a `Files not reviewed` block, while on one pull request 21 of 51 reviews counted fewer files reviewed than changed. None of them named a file it skipped |
| what makes a file go unreviewed | **the size of that file's own diff, not of the whole change.** Measured over 51 reviews of one pull request: every drop in the count came with one more file's diff (`git diff <merge-base> <head> -- <file>`, in bytes) crossing one threshold, and no drop came without one: the first when one file's diff grew from 101 462 bytes to 106 426, the second when another's grew from 100 775 to 102 856. The threshold lies above 101 462 and at most 102 856. A pull request of 360 611 bytes over 52 files, none past 37 815, kept every count whole over 22 reviews. Every review measured that states an effort level states `Lite`, and which file a short count dropped was never named — that it is the large one is an inference |
| a reply in a review thread | **posts as a review of its own, under the replier's login**: `COMMENTED`, an empty body, and that one reply as its only inline comment, its `commit_id` the head at the moment of replying — so a later force-push leaves it pinned to a commit the branch no longer has. Measured over 18 pull requests of one repository: 53 thread replies and 53 such reviews, one reply apiece — the replies traced on one of them posted through REST `pulls/<n>/comments/<id>/replies`; and across 39 threads answered through GraphQL `addPullRequestReviewThreadReply`, 40 replies, every one the same. The GitHub MCP server's reply tool is unmeasured. A session replies under the user's own login, so these read as a person's reviews on the timeline and in the reviews feed, and they are the session's ([`invariants.md`](invariants.md)). GitLab's counterpart is unmeasured |
| a review that could not run | **posts as a review like any other**: `COMMENTED`, the body a single sentence saying it encountered an error and could not review, with no counts. Measured twice on one pull request. Its `commit_id` is the commit it failed on — which names the head that failed, never a head that was reviewed; a reading by commit alone takes it for a review of that head, and only its body says otherwise |
| an automated re-review of a pushed head | **a fresh pass over the whole change, not a check of the push.** Measured over 1 089 Copilot re-reviews on 119 pull requests across five repositories, 8–18 September 2026: in the four whose product is code, of the 258 re-reviews after a push changing only documentation or comments, 8–10% commented on a line the push changed, and no defect they found sat on one; an unchanged head, re-reviewed, drew new comments on 11 of 17. GitLab's counterpart is unmeasured |
| `Review effort level` in an automated review body | **unmeasured as a signal.** All 92 of the 94 reviews above that state it say `Lite`, so what another level changes has not been seen — a fact about the round, never grounds for a step |
| a pull request with no reviewer verdict | may carry no request at all rather than a withheld one — measured on four pull requests whose base was a feature branch, which carried no `copilot_code_review` rule and no reviews |
| `requested_reviewers`, and `gh pr view --json reviewRequests` | **empty from the moment a review request registers until its review posts** — both read the same field, so a wait armed on either never fires. The timeline is where a standing request is legible |
| `dismiss_stale_reviews_on_push` | **unmeasured here, and the claim it is usually written with is untested.** The distinguishing case — a push that changes no diff, with an approval standing — did not occur in 60 merged pull requests across four repositories, though 13 of them force-pushed. Read what the pull request reports rather than predicting from the setting |

## Issues and their vocabulary

| signal | what it actually is |
|---|---|
| a native issue-type field | **GitHub's belongs to organisation-owned repositories and holds one type per issue; GitLab's configurable work item types are a paid-tier feature configured on the top-level group.** `gh` carries it as `issueType` and `--type`, `glab` not at all ([`forge-docs.md`](forge-docs.md)); a flag naming the type an issue is merely filed under is not this value, whatever it is called |
| a `404` from a type-definitions endpoint | **the same answer whether the feature is absent or invisible to this token.** Absent only once something else confirms the token reaches this repository — and say which of the two you concluded |
| a `200` from a type-definitions endpoint | **no proof the repository has types.** Measured on a user-owned repository: `repos/{owner}/{repo}/issue-types` listed Task, Bug and Feature, while GraphQL `repository.issueTypes` answered `null` and no issue in the REST list carried a `type` key. Read the GraphQL field: `null` is no types here, whatever the endpoint lists |
| label cardinality | **GitHub enforces none of it.** GitLab enforces one-value-per-key for `key::value` labels on a paid tier only, and by *replacing* the sibling rather than refusing the new one, splitting the key at the **last** `::`. Probe for it rather than assuming it |
| a label name the caller did not just read | **created, on GitLab**, so a typo joins the set permanently; on GitHub labels passed while creating or updating an issue are dropped in silence where the caller has no push access. Confirm the labels that came back, not the exit status |
| a `404` on an issue's comment feed | **an answer, not a silence.** Measured on both: `gh: Not Found (HTTP 404)` and `glab: 404 Not found (HTTP 404)` — the issue is not there, which a caller fixes by correcting the coordinate rather than retrying. It is also what either forge answers where the token cannot see the issue, and the two are indistinguishable from outside |
| a GitLab label listing | carries the group's **inherited** labels, which apply, and **archived** ones, which do not |

## Reading a slice of issues

| signal | what it actually is | measure instead |
|---|---|---|
| `gh issue list --limit <n> --json` with the link fields | **one GraphQL request per 100 issues up to `--limit` — 30 where none is given — however many links they carry.** The nested sizes are gh's own — in 2.100.0 `subIssues(first:100)`, `blockedBy(first:50)` and `blocking(first:50)`, each with `totalCount`, and `comments`, `labels`, `assignees` and `closedByPullRequestsReferences` at 100. Measured: 55 open issues with every link, 1 request, ~1.3 s, 5–7 points of the 5 000 an hour; the same links read two calls per issue, 110 calls and ~60 s; 1 024 issues of `cli/cli`, 11 requests, 55 points, ~23 s | one request per page for the whole slice; a call per issue only for the issues picked out of it |
| the cost of a GraphQL read | **set by the outer page and by how many nested connections select nodes — not by their sizes.** Measured on a ladder of queries: `cost ≈ round((1 + outer first × nested connections selecting nodes) / 100)`. The inner `first` moves nothing, and a connection selecting only `totalCount` adds nothing and needs no `first` | `totalCount` alone wherever the nodes are not read |
| what a slice read costs the reader | **context, not quota.** Measured on the same 55 issues: 464 KB with `body` and `comments`, 88 KB without them, ≈145–220 bytes an issue in a JSONL projection of one's own | the slice without bodies and comments; those only for the issues picked |
| a bulk REST form for links | **none.** No endpoint in the REST issues category lists a repository's dependencies or its parent/child pairs; the issue list carries `sub_issues_summary`, `issue_dependencies_summary` and `parent_issue_url` — counts, and a parent without its state. **GitLab:** no REST for work items (`/projects/:id/work_items` answers `404`), links one call per issue, and of the blocking counters only `blocking_issues_count`; GraphQL reads 50–100 issues with milestone, hierarchy and links in one request | GraphQL, on both |
| a field the CLI build or the server lacks | **fails the whole call, never just the field.** `gh issue list --json` naming a field outside its 27 answers `Unknown JSON field` and nothing else — `issueDependenciesSummary` and `duplicateOf` are two such. gh builds the query without reading the server's schema, so on GHES 3.17 and 3.18, which lack `blockedBy`, `--json …,blockedBy` fails outright — derived from gh's source and the GHES schemas, unmeasured live. **GitLab**, measured on CE 18.7: `blocked`, `blockedByCount` and `blockingCount` are not in the schema, a query naming any of them fails whole with `undefinedField`, and `WorkItemRelatedLinkType` holds `RELATED` alone | only what the build and the server carry (`forge-docs.md`); on GitLab, blockers counted on the client |

## Pages, and what a page leaves out

| signal | what it actually is | measure instead |
|---|---|---|
| `--paginate` | **the two CLIs answer it oppositely.** `gh` prints one JSON document per page, concatenated — parsed as one document that is a syntax error, and as the first page it silently IS the first page. `glab` merges every page into one array, which its own help states. A reader written for either fails on the other | split `gh`'s output on brace depth; parse `glab`'s as one array |
| `gh api graphql --paginate` | **pages only through a variable named exactly `$endCursor`, and only on the outermost `pageInfo`.** Measured: a query paging under any other name looped — 235 requests in 120 s; a query selecting any nested `pageInfo` stopped after the first page, exit 0. `--paginate --slurp --jq` is refused, exit 1, and `--paginate --jq` filters each page on its own. **`glab api graphql --paginate`:** the same `$endCursor`, and `count` selected before `pageInfo` stops it after one page too | the cursor named `$endCursor`, `pageInfo` on the top connection only, and a filter run over the slurped whole afterwards |
| the exit status of `gh api graphql` | **1 whenever part of the answer errored — with the good part already on stdout** | `data` and `errors` both, never the status alone |
| `nodes(ids:)` past 100 ids | **a fatal error for the whole query.** The same ids as aliases answer what resolves and an error for the rest | ids in batches of 100, or aliased with `errors` read |
| the collections `gh --json` flattens | **truncated without a count.** `labels`, `assignees`, `comments` and `closedByPullRequestsReferences` arrive as bare arrays read at `first: 100`; only the link fields keep `totalCount`, so only their truncation shows. `gh pr list --json files` reads `files(first: 100)` with no count either | the link fields' `totalCount` against their nodes; `changedFiles` against the length of `files`; for the rest, a GraphQL read that asks for `totalCount` |
| `glab issue list` | **`-P` above 100 answers 100, and `-A` is every state, not every page.** Its `-F` is `--output-format` (`details`, `ids`, `urls`), so `-F json` prints text — on `glab issue view` the same `-F` is `--output`. `--output json` drops `blocking_issues_count`, `type` and `has_tasks` | `-p` page by page until a short page, or `glab api` |
| a field from a file, on `gh api` and `glab api` | **`-f x=@<file>` sends the string `@<file>` itself, exit 0 — only `-F` reads the file.** Measured on gh 2.100.0 and glab 1.97.0 through each forge's markdown-render endpoint: `-f text=@<file>` rendered the path, `-F text=@<file>` the file's content. On GitHub eight comments went up as `-f body=@<path>` — seven thread replies on one pull request, one issue comment — and each was stored as that one-line path; seven edits through `-F body=@<path>` stored byte for byte what their files held | `-F <field>=@<file>`, and the stored field read back and compared with the file |
| `glab api` input | **list fields passed as `-f 'x[]=v'` are dropped without a word**; and `--input` sends no `Content-Type` ([gitlab-org/cli#8517](https://gitlab.com/gitlab-org/cli/-/issues/8517)), which each API refuses in its own words. Measured on glab 1.97.0: REST answers `415`, `The provided content-type '' is not supported`; GraphQL answers `Unexpected end of document` — nothing there names the header | a JSON body through `--input` with `-H 'Content-Type: application/json'` |

## Links, search and milestones — wrong without an error

A row here that names no GitLab counterpart has none measured.

| signal | what it actually is | measure instead |
|---|---|---|
| a relationship qualifier in search | **honoured by advanced search alone** — GraphQL `search(type: ISSUE_ADVANCED)`, REST `advanced_search=true`; the default search takes it without an error and answers something else. Measured on one slice of 55 issues, default against advanced: `has:sub-issue` 55 against 3 and `has:parent-issue` 55 against 25 — an unknown `has:` is ignored; `is:blocked` 0 against 6 — an unknown `is:` matches nothing; `blocked-by:` and `blocking:` 0. `parent-issue:`, `sub-issue:` and `no:parent-issue` answer in both. A value is `OWNER/REPO#N` only — a bare number matches nothing. None of these qualifiers is on GitHub's pages about searching issues or on its search REST reference | advanced search, `OWNER/REPO#N` in full, and a control query whose count is already known |
| `is:blocked` | **open, and blocked by an issue that is open** — one whose blockers are all closed is not in it | `has:blocked-by` for any blocker at all |
| several labels in one filter | **either label in one place, both labels everywhere else.** Measured on `cli/cli`, `bug` 2 256 and `gh-issue` 133: GraphQL `repository.issues(filterBy: {labels: [a, b]})` answered 2 347; search `label:a label:b` — what `gh issue list --label a --label b` compiles to — and REST `issues?labels=a,b` answered 42. **GitLab**, measured on `gitlab-org/cli`: GraphQL `workItems` and `issues` with `labelName: [a, b]`, and REST `labels=a,b`, all answer both labels — 546 and 17 gave 15 | one label per GraphQL `filterBy`, intersected on the client — or search, or REST |
| `gh issue list --search`, `--label`, `--type`, `--milestone` | **a search under a listing's name**, compiled to `search(type: ISSUE_ADVANCED)` with a search's limits: capped at 1 000 results, which the terminal warns of and JSON output does not; and `state:open` added unless gh recognised a state qualifier — `parent-issue:` and `reason:` it does not. Measured: `--search 'parent-issue:tvip/tvip-nexus#427'` answered 14 of 35 children, `--search 'reason:completed'` 0 of 361. `--milestone` with a title that matches none answers an empty list, exit 0 | `--state all` whenever the query carries the state itself; `issueCount` of the same search against 1 000, the query split where it is over |
| a link node in `gh --json` | **carries no `repository`** — `id`, `number`, `state`, `title`, `url` only, though the query asks for it and the terminal prints it, so an edge to another repository reads as a number in this one. `closedByPullRequestsReferences` is the reverse: `repository`, and no `state` | a link keyed by its `url` |
| a link whose far end the token cannot see | **vanishes, leaving nothing behind**: gone from `nodes`, from `totalCount`, from REST and from the timeline; `parent` reads `null`; exit 0. Measured on `elastic/kibana`: 17 of the 88 issues under `is:blocked` showed no blocker at all. `subIssuesSummary.total` and `issueDependenciesSummary` count past the token's rights, so a summary above the visible edges is the one sign; a hidden parent has no counter, and only `has:parent-issue` finds it. Through `gh --json` only hidden children show — `issueDependenciesSummary` is not among its fields. GitLab's counterpart is unmeasured | the summaries against the visible edges, through GraphQL wherever dependencies matter |
| a filter by update time, over links | **blind to every change a link makes.** Measured on `tvip/tvip-nexus`: 7 issues carry a `blocked_by_added` / `blocking_added` / `parent_issue_added` dated after their own `updatedAt`, and neither REST `since=` nor GraphQL `filterBy: {since}` returned one of them — 175 issues came back for one pin, none of the seven among them. **Closing the other end of an edge moves nothing either** — 103 parent→child pairs and 3 the other way, where only the closed end's own `updatedAt` rose — and a `referenced` cross-reference moves nothing. What does see them: `timelineItems(since:, itemTypes: [the eight link events]) { filteredCount }`, whose `totalCount` instead ignores `since` and marks the whole repository. Measured against the REST `/issues/events` feed at three pins, issue for issue (89=89, 75=75, 0=0), cost 1 per 100 issues — and each event lands on **both** ends, so counting by issue number doubles the edges. That REST feed takes `since=` and ignores it, answering the same window byte for byte. An event's `created_at` trails the `updatedAt` it belongs to by a second or two. **GitLab:** `workItems(updatedAfter:)` catches neither a parent set nor a link created; `LinkedWorkItemType` carries `linkCreatedAt` and `linkUpdatedAt`, the hierarchy carries no time at all, and nothing counts events | the slice's edges read again and set against an earlier reading of it (`scripts/issue-slice.mjs --since`), the count beside it as a cross-check, and the next moment taken from the response's own `Date` |
| the REST issue list | **carries pull requests too**, each marked by a `pull_request` key; and `gh issue view` given a pull request's number answers with that pull request, exit 0 | rows with `pull_request` dropped; the `url` of what `view` returned checked |
| `--parent` and `--add-sub-issue` | **move an issue away from its current parent without a word** — both always send `replaceParent: true`. The link edits of one `gh issue edit` run in parallel with their errors joined, so a partial failure leaves some edges written. Read from gh 2.100.0's source, never run | the parent read before one is set, and the edges read back after any link write |
| a milestone's counters | **count pull requests beside issues** — `open_issues`, `closed_issues`, `progressPercentage`: measured on `microsoft/vscode`, 10 closed were 1 issue and 9 pull requests. `sub_issues_summary.completed` counts a child closed as `not planned` among the completed, and `--json milestone` carries no `state` and no progress at all | `milestone.issues(states:)` through GraphQL for issue counts; the milestones REST with `state=all` for state; each child's `stateReason` for completion |
| a milestone on write | **`-m` finds one by title, among open milestones only.** Milestones belong to the repository alone — GitHub has none on the organisation, and `gh` no `milestone` command. **GitLab:** a project's listing hides the group's milestones unless it asks with `include_ancestors` | the milestone resolved before the write; on GitLab, listed with `include_ancestors` |

## What the terminal output leaves out

The JSON carries every one of these; only the printed form drops them.

| output | what it leaves out | the form that carries it |
|---|---|---|
| `gh issue list` | the milestone — its columns are ID, STATE, TITLE, LABELS, UPDATED | `--json` |
| a `--template` reading `{{.milestone.title}}` | **fails on the first issue with no milestone**: `nil pointer evaluating interface {}.title`, exit 1, the rows before it already printed | `{{with .milestone}}{{.title}}{{else}}—{{end}}`, or `--jq '.milestone.title // "—"'` |
| `gh issue view`'s milestone | everything but its title | `--json milestone` |
| `gh issue view`'s `Parent:`, `Blocked by:`, `Blocking:` | the state of the other end — while the sub-issues section does print it | `--json parent,blockedBy,blocking` |

No upstream request tracks these; the nearest are
[cli/cli#14413](https://github.com/cli/cli/issues/14413) and
[cli/cli#8744](https://github.com/cli/cli/issues/8744).

## Limits

| limit | how it announces itself | what to do |
|---|---|---|
| a comment body's maximum | **a refusal saying the body is too long, and naming the wrong number in the wrong unit.** The cap is **262 144 bytes of UTF-8**, measured on both sides of the boundary for a comment's REST create and edit alike: 262 144 bytes stored and 262 145 refused — and in Cyrillic 131 085 characters at 262 144 bytes stored, 131 086 at 262 146 refused. REST refuses with `422`, **spelled differently per call**: `body is too long (maximum is 65536 characters)` on an edit, `Body is too long …` on a create. **The status belongs to REST alone**: GraphQL's `updateIssueComment` refuses the same 262 145 bytes under `HTTP 200`, as an `UNPROCESSABLE` entry in `errors` spelled `Body is too long …`. A refusal saying nothing about the length is transport, not the cap: an empty reply or a response that does not parse refused 22 of 33 writes of one body under the cap, stored between them — one such refusal came from a write that had landed — and a secondary-limit `403` arrives the same way | measure **UTF-8 bytes** against the cap before writing, and archive ahead of it. Answer a refusal whose message says the body is too long by archiving — matched case-insensitively, whichever API carried it; answer any other refusal by reading the body back, and writing again only if it did not land. GitLab's own limit is unmeasured |
| an issue body's maximum | **nothing, over REST.** The cap is the same 262 144 bytes, and a `PATCH` one byte over it answers `200 OK`, echoes the new body in its response and lists the edit in `userContentEdits` — while the stored body stays the previous one. Measured twice at 262 145 bytes. `gh issue edit` (GraphQL `updateIssue`) refuses the same body loudly, as `Body is too long (updateIssue)`, naming no number | measure bytes before writing; write an issue body through `gh issue edit`, and after any write to it read the body back rather than the response. GitLab's own limit is unmeasured |

## What is not here

A number nobody measured, and a behaviour that a document asserts but no run
confirmed. Where a row would need either, the row says it is unmeasured — an
unmeasured row is a question someone can answer later, while a confident one that was
never checked is a wrong answer nobody will question.
