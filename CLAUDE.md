# Repository guide for Claude Code

This repo is a **Claude Code plugin marketplace** named `hacker-cb-plugins`. It both *is* a marketplace (`.claude-plugin/marketplace.json`) and *hosts* the plugins it lists — first-party plugins under `plugins/` and thin external-MCP wrappers under `external_plugins/`.

Official documentation — consult before changing structure. The raw `.md` URLs are WebFetch-friendly and on Claude's preapproved doc domains, so fetch them on demand (do **not** vendor or `@`-import them — `@` imports local files only, and these large refs would load in full every session).

**Start from the index**: [llms.txt](https://code.claude.com/docs/llms.txt) lists every docs page as one line (title, `.md` URL, one-sentence summary). Fetch it when the page you need isn't in the shortlist below, or to confirm a URL still exists before trusting one from memory — pages get renamed and merged (custom slash commands, for instance, now live inside the Skills page).

Shortlist for this repo:

- [Plugins](https://code.claude.com/docs/en/plugins.md) — the authoring guide.
- [Plugins reference](https://code.claude.com/docs/en/plugins-reference.md) — manifest schema, component dirs, `${CLAUDE_PLUGIN_ROOT}`, version pinning, cache/file-resolution.
- [Marketplaces](https://code.claude.com/docs/en/plugin-marketplaces.md) — `marketplace.json` schema, hosting, install flow.
- [Plugin dependencies](https://code.claude.com/docs/en/plugin-dependencies.md) — version constraints between plugins, bundling a curated set behind one install.
- [Plugin relevance](https://code.claude.com/docs/en/plugin-relevance.md) — the marketplace-entry block that makes Claude Code suggest a plugin when the user's work matches.

## Conventions

- **One themed plugin per domain** under `plugins/hcb-<domain>/`, each with its own `.claude-plugin/plugin.json`.
- **Naming**: plugin names are prefixed `hcb-` (`hcb-<domain>`). Skills / commands / agents are **not** prefixed — the `hcb-<domain>:` namespace already shows provenance in the `/` menu.
- **Skills** live at `plugins/hcb-<domain>/skills/<skill>/SKILL.md`; frontmatter needs a `description` (≤ 1024 chars). Supporting files (`references/`, `scripts/`) sit next to `SKILL.md`; ones shared by more than one skill go a level up, in `plugins/hcb-<domain>/references/`, linked from each skill by relative path.
- Component dirs (`skills/`, `commands/`, `agents/`, `hooks/`) go in the **plugin root**, never inside `.claude-plugin/`.
- **Versioning**: a plugin's `version` (semver, in its `plugin.json`) is the **only** version in the repo — there is no marketplace-level version and no release tags/artifacts. `scripts/validate.sh` enforces that it is valid semver and not duplicated in the marketplace entry.
- **External MCP wrappers** live under `external_plugins/<name>/` (not `plugins/`): a thin `plugin.json` + `.mcp.json` wrapper around a third-party / own **npm** MCP server, mirroring the `anthropics/claude-plugins-official` layout. Use the **upstream package name** (no `hcb-` prefix) and **omit** `version` — the server is versioned in its own repo and pinned via `@latest` / `@x.y.z` in `.mcp.json`. `scripts/validate.sh` exempts `./external_plugins/*` from the `hcb-` prefix and the per-plugin-semver axis (both still enforced for `./plugins/*`). See [`external_plugins/markdown-docs`](external_plugins/markdown-docs) for the worked example.
- **Claude Code's own paths**: never hardcode one — and don't confuse the two mechanisms that look alike. `${CLAUDE_CONFIG_DIR}` is a real environment variable the *user* may set: readable by any process, defaulting to `$HOME/.claude` when unset, so shell code writes `${CLAUDE_CONFIG_DIR:-$HOME/.claude}` ([env vars](https://code.claude.com/docs/en/env-vars.md), and what lives under it in [the `.claude` directory](https://code.claude.com/docs/en/claude-directory.md)). `${CLAUDE_PLUGIN_ROOT}` is **not** an environment variable you can read: it is a placeholder Claude Code substitutes textually, and only in the fields the plugins reference lists — skill and agent content, hook and monitor commands, the MCP and LSP server fields. It reaches a process as a real variable only when Claude Code spawned that process from plugin config (hooks, monitors, MCP, LSP); in a plain `Bash` call it is empty, and in a `README.md`, `CLAUDE.md` or `references/*.md` it stays literal text ([plugins reference](https://code.claude.com/docs/en/plugins-reference.md)). **`env-vars.md` documents the first and not the second** — it is the reference for variables a process reads, and a substitution placeholder is not one, so go to the page that owns the mechanism rather than assuming one page lists every name. Note too where a path's internal layout is undocumented: anything relying on it degrades gracefully instead of failing.
- **Never hardcode branch or remote names.** `master`, `main`, `dev`, `develop`, `trunk` — every repo picks its own, so a name written into a skill is wrong somewhere, and a guess that *resolves* is not a guess that is *right*. `origin` is the same kind of guess: a repo may have one remote under another name, and in a fork checkout `upstream` is the real base while `origin` is your own copy. Resolve both at runtime: `<remote>/HEAD` (verify the ref it names still exists — `symbolic-ref` reads the pointer without dereferencing it), `git ls-remote --symref <remote> HEAD`, the forge's own default-branch field, or the open change request's base. Write `<base>` / `<default>` / `<remote>` wherever a name would otherwise be spelled out, and compare against the remote-tracking ref (`<remote>/<default>`) rather than the bare name — a clone that only checked out feature branches has no local default branch, and `git branch --merged <default>` there dies with "not a valid object name". Naming a branch as an *example* of a non-default base is fine; naming one as a value to try is not. Two exceptions: this repo's own CI config, which targets a real branch of a real repo; and a *last* rung that tries `origin` (or `upstream`) by name after every resolution step has failed — that is a documented preference order, not an assumption, and it must still stop rather than guess when several remotes exist and none is preferred. See [`plugins/hcb-dev/references/base-resolution.md`](plugins/hcb-dev/references/base-resolution.md).
- **Links.** A pointer that sends the reader to another file in this repo is a markdown link, and its path is **relative to the file it is written in** — that is how every renderer, every editor and the link checker resolve it, and it is the form the skills docs themselves show. The link text equals the path when the text is written as a path; ordinary prose (`[MIT](LICENSE)`) is free. Repeat pointers to a file already linked in the same document stay bare backticks — a second link adds nothing. Lists that say *read this* (`## Reference files`) are always links. Never put `${CLAUDE_PLUGIN_ROOT}` in a link: it buys nothing a relative path lacks, and it is wrong outside skill and agent content. A shared reference states what it owns and why it lives outside any one skill, but does **not** enumerate who reads it — the links pointing at it are that record, and the map for humans lives once, in the plugin's `README.md`. External URLs are ordinary markdown links — `[text](url)`, same as internal ones. What changes with the audience is the **target**, not the form: files Claude reads as instructions (`CLAUDE.md`, `SKILL.md`, `references/`) point at the `.md` page where one exists, so a fetch returns raw markdown instead of HTML; files written for people (`README.md`, `CONTRIBUTING.md`) point at the rendered page. The `.md` variant is not universal — `code.claude.com/docs` serves one for every page, GitHub Docs only for some — so check the specific URL before adding the suffix rather than appending it by rule. `scripts/validate.sh` enforces the suffix for the docs domain it knows; `lychee` is what proves a link resolves at all.
- **Never write a positional parameter in a `SKILL.md` or an agent file.** Claude Code substitutes those in skill and agent content with the words of the invocation arguments (`$N` is shorthand for `$ARGUMENTS[N]` — [skills](https://code.claude.com/docs/en/skills.md)), so a shell `budget=` assignment or an `awk` field reference inside a run block reaches the reader already rewritten — as whatever the caller happened to type. The block is then not merely wrong but *plausible*, which is worse: it looks runnable. Pass values through named variables set before the call, and use `sed` or `awk -v` where field references would be needed; where a literal is genuinely meant — a price, a verbatim snippet — the docs' backslash escape says so. `$@`, `$*` and `${VAR}` are not substituted and are safe. Two places are deliberately outside this: a `references/*.md` reaches Claude through `Read`, which returns the file verbatim, and `commands/` is where the substitution is the *feature* — which is exactly why a shell positional must not sit beside it there. `scripts/validate.sh` enforces it for skills and agents.
- **Authoring skills**: what belongs in a `SKILL.md` and a `references/*.md` — and what stays out of both — is [`.claude/rules/skill-authoring.md`](.claude/rules/skill-authoring.md), which loads whenever you work under `plugins/`. For triggering, use the **skill-creator** methodology — draft the `description` per its Skill Writing Guide (trigger-focused, slightly "pushy"), lay the body out by progressive disclosure, and tune triggering with its description-optimization loop (`run_loop.py`). On Claude Code web it's mounted at `/mnt/skills/examples/skill-creator`; otherwise pull it from Anthropic's public skills repo.

## Commands

```bash
bash scripts/validate.sh         # structural validation + naming convention (the CI gate)
```

```bash
lychee --no-progress './**/*.md' '.claude/**/*.md'    # every link, external ones included
```

When you add or change a plugin/skill, run `scripts/validate.sh` and keep `README.md` and `CONTRIBUTING.md` in sync.

**Whenever you add or edit a link, run `lychee` online** — without `--offline` — so external URLs are actually fetched. CI splits the two: the per-PR job runs `--offline`, which skips every `http(s)` URL so a docs host having a bad afternoon cannot fail a pull request, and a weekly job checks the external ones. That means a broken external link you introduce today is nobody's error until the next Monday unless you check it yourself. See [`CONTRIBUTING.md`](CONTRIBUTING.md) for step-by-step instructions.
